## 1. Objective

Determine whether a **carefully controlled** improvement of the frozen 12D GRU
forward-speed model can lower velocity error **and** improve downstream
dead-reckoning navigation, while staying lightweight and causal. The frozen 12D
GRU ("v1") remains the permanent baseline and was neither retrained nor modified.

Observations, one line each, evidence only:

* **E05 window length** — T=60 is the single biggest win (val RMSE −5.2 %, MAE −11.2 % vs E05a T=20). T=40 did **not** help; longer is not monotonically better.
* **E02 LR scheduling** — a genuine, smaller improvement (−3.6 % val RMSE vs v1), keeps T=20.
* **E01 Huber** — δ=1.0 slightly worse, δ=2.0 ≈ parity. No support for "Huber is physically better" here.
* **E03 tighter grad clip, E04 longer patience** — no improvement; documented and dropped.
* **E06 small GRUs** — all within ~0.6 % of each other and ~1 % worse than v1; the 15 k-param h64·l1 is the cheapest at a modest accuracy cost.
* **E07 TCN-GRU** — competitive MAE (4.97) at 23 k params, but RMSE ≈ E05a T=20; does not beat the T=60 GRU. Discarded as the final model, kept on record for 16B.

**Paired FDE: median 229.8 → 177.2 m (−22.9 %); GRU v2 wins 69 % of cases;

long-outage error is still heading-dominated, which is the Step-15 problem, not
16A's. But on the bulk of cases the better velocity model produces a
statistically significant, ~23 % reduction in final drift.

**Answer to the section-26 question: yes — the lower-velocity-error GRU v2 does
improve downstream navigation** (median FDE and ATE down, significant, 69 % case
win rate), without any change to the filter.

## 17. Limitations

1. v1/v2 regime tables use different window lengths (T=20 vs T=60); comparable at the sequence level, not bit-for-bit per window.
2. v2 is slightly worse than v1 in the 0–1 m/s / stationary regime.
3. Reproduced v1 **validation** RMSE (7.06) differs from the historic tuning-trial value (6.84) because the frozen final fit used a different seed; the frozen **checkpoint** and its **test** metric reproduce exactly.
4. No CPU/Android/edge benchmark; no quantisation; no ONNX/TFLite (all deferred).
5. Navigation check inherits Step 14's predict-only-during-outage, constant-heading model — long-outage drift stays heading-limited; SIH < 10 % is still not met by any method.
6. `scipy` Wilcoxon used for the paired test; 71 of 72 cases.

## 18. GRU v2 — ACCEPT / REJECT

**ACCEPT.**

* Validation: RMSE, MAE and R² all improved vs frozen v1 (6.696 vs 7.064; 4.818 vs 5.428; 0.508 vs 0.453).
* Held-out test: RMSE −13.2 %, MAE −13.9 %, R² +0.105 — no tuning after freeze, v1 reproduces exactly (no leakage).
* Downstream: median FDE −22.9 % (significant, 69 % case win rate) through the **unchanged** EKF.
* Cost: identical parameter count / model size, latency still sub-0.02 ms/window, fully causal.
* The single change (T 20 → 60) is minimal and defensible.

GRU v1 remains the valid, reproducible baseline and is untouched.

## 19. Recommendation for the next phase

1. **16B — TCN-GRU challenger.** E07 already shows a 23 k-param causal TCN-GRU matching T=20 GRU MAE; give it the T=60 window and a proper tuning pass. Target: v2 accuracy at ≤ ¼ the parameters for edge deployment.
2. **16C — lightweight Transformer** only as a later, separate challenger — not to be adopted purely for being "more advanced" (§23).
3. Independent of 16B/16C: the navigation ceiling is **heading during outage**, not speed. The largest remaining SIH gain is a heading/turn-rate aid or map-matching in the Step-15 line, not a bigger speed model.
4. Before any mobile demo: CPU/edge latency + quantisation benchmark for v2 (and the eventual 16B model).
