# IO-VNBD — EDA + GNSS-blackout drift benchmark (findings)

Scope: the **Synchronised / Categorised** subset of IO-VNBD — 72 row-aligned
smartphone (`S-`) + vehicle (`V-`) trip pairs, 1 345 km, 29.9 h, all recorded in
the UK, all at 10 Hz. Generated by `scripts/01_build_catalog.py`,
`scripts/02_eda_report.py`, `scripts/03_run_drift_benchmark.py`.

## 1. Dataset is usable, after fixes

| Item | State |
|---|---|
| Raw zip you supplied | every CSV was a 130-byte Git-LFS **pointer stub** — 0 data rows |
| Fixed | `git lfs pull` from `github.com/onyekpeu/IO-VNBD` → 564 real CSVs, 1.79 GB, checksum-verified. Now at `dataset/IO-VNBD/` |
| Row alignment | **genuine** — phone-GPS-speed vs vehicle-speed corr 0.88–0.97; phone-GPS-course vs vehicle-heading mean offset ≈ 0.3°, concentration 0.90–0.96 |

### Data quirks the loader has to absorb (`src/iovnbd/schema.py`, `loader.py`)

1. **Header mojibake / units in parens.** `ACCELEROMETER X (m/s²)` arrives as
   `ACCELEROMETER X (m/s�) ` with a trailing space; the phone `ORIENTATION`
   columns put the axis *inside* parentheses (`ORIENTATION (Yaw) (°)`). Mapping
   is done on whole-token keyword matching, not substrings.
2. **Two phone layouts.** Categorised trips use `GYROSCOPE Yaw/Pitch/Roll` +
   `ORIENTATION (Yaw)`; the uncategorised pool uses `GYROSCOPE X/Y/Z` +
   `ORIENTATION (Azimuth)`. Same signals, canonicalised to `gyro_x/y/z`,
   `ori_yaw/pitch/roll`.
3. **Phone `GPS SPEED (Kmh)` is actually m/s.** Verified against vehicle
   ground-truth speed on every trip (ratio 0.95–1.00). The header label is
   wrong. Loaded as `gps_speed_ms`.
4. **Timestamps differ.** Phone `DATE` is local (BST); vehicle
   `Time Since Start of Day` is UTC — a clean 1 h offset. Phone
   `TIME SINCE START (ms)` is unreliable on several trips; the loader rebuilds
   the phone clock from `DATE` and rebases every trip onto the vehicle clock.
5. **Vehicle `Height (km)` values are metres.** Loaded as `height_m`.
6. **9 of 72 pairs are off by 1–230 rows** (mostly the `Vf` driver); the loader
   truncates to `min(len(S), len(V))`.
7. **Logging gaps.** A few trips contain multi-hundred-second holes
   (GPS/​comms dropouts). Blackout windows that straddle a `Δt > 0.5 s` jump are
   rejected.

## 2. EDA headline: the phone IMU is mostly **decoupled** from vehicle motion

`outputs/catalog.csv` adds two coupling metrics per trip (best correlation over
±20-sample lag, moving samples only):

| metric | what | median | trips with \|r\|>0.3 |
|---|---|---|---|
| `imu_r_gyro_vs_yawrate` | best phone gyro axis vs true yaw-rate | 0.15 | 19 / 72 |
| `imu_r_acc_vs_vehlong`  | \|phone linear-accel\| vs \|vehicle long-accel\| | 0.14 | — |

* Only **19 / 72 trips** have a phone IMU that carries a usable vehicle-dynamics
  signal (e.g. `M`, `S1`, `S3c`, `Vta11` reach gyro \|r\| 0.6–0.8). On the rest
  (`S2`, `Vf-Vfa02`, `Vta29`, `Vtb05`, `Vw14b`, …) the phone gyro and even
  Android's fused `ORIENTATION` yaw are **uncorrelated (r ≈ 0)** with true
  heading rate — the phone was resting loose, in an arbitrary pose, dominated by
  vibration.
* Longitudinal-acceleration coupling is weak on **every** trip (best ≈ 0.4).
* Consequence: a single static phone→vehicle rotation cannot rescue heading;
  `src/iovnbd/align.py` estimates one from gravity + GPS-course and reports a
  `quality` score, which is low on most trips (the DR code then falls back to a
  frozen course).

### Other EDA facts (`outputs/eda/summary.txt`, `outputs/eda/*.png`)

* Phone sample rate is a tight 10 Hz on all trips; ≤ 3 gaps > 0.3 s each.
* Phone GPS accuracy: median 4 m, 95th-pct ≤ 6 m; `frac_gps_poor` ≤ 0.14.
* Speed range: median trip mean 42 km/h, max 132 km/h — motorway + town mix.
* `truth_dr_drift_pct` (dead-reckon with **true** speed and **true** heading,
  60 s window) is < 1 % on 54 / 72 trips → loader + geometry + integrator are
  sound and those V-files are internally consistent. **`Y1` = 4.8 %** — its
  V-file dynamics disagree with its own position track; excluded.
* Benchmark-usable after all filters (full IMU, sane units, ≥ 0.3 km, mostly
  moving, ≥ 60 s, truth-consistent): **50 / 72**.

## 3. Synthetic GNSS-blackout drift benchmark

`src/iovnbd/blackout.py` engineers outages (IO-VNBD has only incidental GPS
loss). Scenarios: `isro_60s` (60 s), `isro_1km` (1 000 m), `tunnels` (8×30 s),
`every_2min`. Anchors are forced onto genuinely-moving segments with a moving
lead-in. Estimator gets everything up to the anchor, propagates with the
non-holonomic constraint (`d/dt` east = v·sin θ, north = v·cos θ), is scored at
outage end. ISRO target: **final drift ≤ 10 % of outage distance**.

**50 trips · 789 windows · all scenarios** (`outputs/benchmark/summary.csv`):

| speed → / heading ↓ | median drift | p90 | pass ≤10 % | reading |
|---|---|---|---|---|
| `truth` / `truth` | **0.25 %** | 0.9 % | **99 %** | pipeline sanity — passes |
| `obd` / `veh_yawrate` | 8.0 % | 66 % | **56 %** | **best classical**: CAN speed + calibrated *vehicle* yaw-rate sensor |
| `wheel_speed` / `veh_yawrate` | 7.9 % | 65 % | 56 % | wheel-odometry speed, same heading — identical, so **heading is the bottleneck** |
| `hold` / `truth` | 15.7 % | 62 % | 36 % | freeze speed at last GNSS value, perfect heading |
| `obd` / `gps_hold` | 26.7 % | 110 % | 23 % | clean speed, **frozen heading** — turns wreck it |
| `hold` / `imu_aligned` | 44 % | 129 % | 10 % | phone-only classical (align quality low → frozen course) |
| `imu_integrate` / `imu_aligned` | 59 % | 193 % | 5 % | **pure phone-IMU dead-reckoning — effectively fails** |

### What the benchmark establishes

1. **The evaluation harness is correct** — `truth/truth` ≈ 0 %, 99 % pass.
2. **Heading dominates the error budget.** Swapping a perfect speed for
   wheel-odometry barely moves the result when heading = `veh_yawrate`; swapping
   a perfect heading for `gps_hold` triples the drift.
3. **Even with a good IMU** (vehicle yaw-rate sensor, calibrated on pre-outage
   GNSS) classical strap-down INS only passes **56 %** and its p90 is 65 % —
   a manoeuvre during the outage still breaks it. → justifies the AI GNSS/INS
   **fusion** model and **map-matching + NHC** correction in the ISRO brief.
4. **With the phone IMU as-is**, classical methods pass 5–10 %. → justifies the
   AI **speed / vibration filter** and **automatic orientation detection**; the
   model has to recover a dynamics signal that raw integration cannot.
5. Speed-hold alone (`hold/truth`) already busts 10 % on longer/variable-speed
   outages (36 % pass) — a learned speed estimator is needed even when heading
   is solved.

## 4. Gaps to close before this is a full ISRO solution

| Need | Status here | Action |
|---|---|---|
| Indian roads / two-wheelers | absent (UK cars only) | collect a fine-tune/validation set |
| 200 Hz FOG-grade IMU path | absent (10 Hz phone) | separate high-rate dataset |
| OSM road graph for map-matching | not bundled | pull an OSM extract; add a matcher stage |
| Engineered long tunnels/underpasses | only synthetic here | keep synthetic + real Indian captures |
| Trips with a usable phone IMU | 19 / 72 | stratify training; weight by `imu_r_*`; use the vehicle-IMU trips as a clean upper-bound reference |
| ML models (speed regressor, heading/fusion net) | hooks only | `dead_reckon(..., speed_source=model.predict)` — plug in an LSTM/TCN next |

## 5. How to reproduce / extend

```bash
python scripts/01_build_catalog.py       # -> outputs/catalog.csv, catalog_brief.md
python scripts/02_eda_report.py          # -> outputs/eda/*.png, summary.txt
python scripts/03_run_drift_benchmark.py # -> outputs/benchmark/{detail,summary}.csv, *.png
```

Plug an ML speed model into the exact same harness:

```python
from iovnbd import load_trip, find_synced_trips, make_blackouts, dead_reckon
from iovnbd.blackout import SCENARIOS

trip = load_trip(find_synced_trips()[0])
win  = make_blackouts(trip, SCENARIOS["isro_60s"])[0]

def my_speed(trip, sl, ctx):        # -> np.ndarray, m/s, len == sl.stop-sl.start
    return model.predict(features(trip, sl))

res = dead_reckon(trip, win, speed_source=my_speed, heading_source="veh_yawrate")
print(res.drift_pct)
```
